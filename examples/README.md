# Example outputs

Everything here was generated by Faultline, not written by hand. Regenerate with:

```bash
make warehouse                 # build the dbt project, both worlds
make fixtures                  # capture them
make examples                  # regenerate everything below from those fixtures
```

`live-verification.txt` and `live-datahub-graph.json` are the two that need a running
instance — `datahub docker quickstart`, then `python demo/verify_live.py`.

| File | What it is |
|---|---|
| `pr-comment.md` | The comment Faultline posts on a pull request. This is the primary artifact — it is what a reviewer actually sees. |
| `scan-report.md` | The full standalone report. |
| `scan-result.json` | Machine-readable result: findings, proof paths, evidence, fingerprints. |
| `writeback-plan.txt` | `faultline writeback --dry-run` — every tag, structured property, incident and audit record that would be contributed back to DataHub. |
| `demo-graph.json` | The demo pipeline as a captured graph snapshot. Scan it with `faultline scan --fixture`. |
| `demo-graph-clean.json` | The same pipeline before the four changes, used as the semantic baseline. |
| `demo-baseline.json` | Column semantics captured from the clean build — what the currency change is diffed against. |
| `live-verification.txt` | The full end-to-end run against a live DataHub — emit, read back, scan, write back, and read the contribution back out. Every line is checked against what the server returned. |
| `live-datahub-graph.json` | The graph as read back *out of* a live DataHub instance, not the dbt capture. Scanning it produces byte-identical findings. |
| `skew-measured.txt` | The train/serve skew measured against the real DuckDB tables — what a distribution monitor sees versus what the model is served. |
| `triage-report.md` | `faultline triage --demo` against a live DataHub: the agent's assessment of each proven finding, the two severities it moved and why, and what the run cost. Produced by Claude Opus 5 reading the catalogue through the official `mcp-server-datahub`. |

## The demo pipeline

A real dbt project on DuckDB (`demo/warehouse/`): three seeds, three staging models, two
marts, an offline and an online feature table, and `churn_propensity_v7` serving live
traffic. Column lineage is parsed from the compiled SQL by DataHub's own `sqlglot_lineage`,
so the proof paths quote actual expressions.

Four changes are applied — each one ordinary enough to merge on a Tuesday:

| Fault | The change | What it does |
|---|---|---|
| leakage | a segment churn-rate rollup computed from the label becomes a feature | offline metrics stop measuring predictive skill |
| skew | the online feature window is changed 30d → 7d during an incident and never restored | the model is served inputs it never trained on |
| semantic | `raw.orders.amount` switches from USD to EUR | every downstream monetary feature silently changes basis |
| compliance | an email-derived column reaches the deployed model | restricted data leaves the governed boundary unlabelled |

Faultline reports **exactly four findings** — one per fault, at its root cause, each with the
lineage path that proves it. The test suite asserts that 1:1 mapping directly
(`tests/test_demo_world.py`), because a demo that over- or under-reports would undermine the
claim that Faultline only reports what it can prove.

Note what is *not* reported. Three other offline/online feature pairs exist in the pipeline
and are built correctly; the skew detector stays silent on all three. The clean baseline
produces zero findings.
